## 목표

`/books/:bookId`가 전자책 리더가 된다. 본문은 화면 한 장 안에 딱 맞는 페이지로 나뉘고(세로 스크롤 없음), 넓은 가로 화면에서는 책처럼 두 쪽이 펼쳐지며, 좁거나 세로인 화면에서는 한 쪽씩 보인다. 페이지는 옆으로 미끄러지며 넘어가고, 손가락이나 마우스로 끌어서 넘길 수도 있다. 챕터 끝에서는 다음 챕터로 이어진다. 화면에 보이는 첫 문장과 마지막 문장 번호를 계산해 두어, 다음 phase에서 위치 알림 API(음악 선곡)에 그대로 쓸 수 있다.

## 배경

- BE PRD의 핵심 시나리오는 "독자가 페이지를 넘기면 그 장면에 맞는 음악이 흐른다"이다. 위치 알림 API(`POST /api/books/{id}/position`)는 화면에 보이는 첫·마지막 문장 번호를 받는다 ([BE API.md](https://github.com/diegesis-labs/BE/blob/main/docs/API.md) 4.6, 4.7절).
- BE는 본문을 문단 → 문장 구조로 주고, 페이지 나누기는 FE가 한다고 정했다.
- 페이지 방식으로 정한 이유: 페이지를 넘기는 순간이 곧 "보이는 범위가 바뀌는 순간"이라 위치 알림 시점이 분명하다. 스크롤은 범위가 계속 바뀌어 묶어 보내는 규칙이 따로 필요하다.
- 처음 계획은 두 쪽 펼침, 넘김 애니메이션, 스와이프를 빼고 "화면에 맞춰 나뉘고 바로 바뀌는" 리더였다. 사용자가 보통의 이북 리더처럼 두 쪽 또는 한 쪽을 화면에 맞추고 슬라이드로 넘기는 경험을 요구해서 범위에 넣었다 (변경 기록 참고).

## 범위

### 하는 것

- **한 화면 고정**: 리더는 화면 전체(`100dvh`)를 쓰고 세로 스크롤이 없다. 본문 영역 = 화면 높이 − 상단 막대 − 하단 막대. 글은 이 영역 안에서만 페이지로 나뉜다 (CSS 다단 방식, 아래 설계)
- **한 쪽 / 두 쪽 자동 전환**: 가로 화면이고 폭 1024px 이상이면 두 쪽 펼침, 아니면 한 쪽. 화면을 돌리거나 창 크기를 바꾸면 다시 나누고, 읽던 문장이 보이는 쪽으로 돌아온다
- **슬라이드 넘김**: 넘길 때 페이지가 옆으로 미끄러진다 (300ms `ease-in-out`, 디자인 시스템 5장 "이동"). `prefers-reduced-motion`이면 바로 바뀐다
- **스와이프·드래그**: 터치와 마우스로 끄는 동안 페이지가 따라오고, 놓을 때 거리나 속도가 기준을 넘으면 넘어가고 아니면 제자리로 돌아간다
- 그 밖의 넘기기: 이전/다음 버튼, 키보드(`←` `→` `PageUp` `PageDown` `Space`), 화면 왼쪽·오른쪽 1/3 탭
- **챕터 경계**: 마지막 쪽에서 넘기면 다음 챕터 첫 쪽이 같은 방향으로 미끄러져 들어온다. 첫 쪽에서 이전으로 가면 이전 챕터 마지막 쪽. 두 쪽 모드에서 챕터는 항상 왼쪽 쪽에서 시작한다
- 위치를 문장 번호로 URL에 저장 (`?chapter=2&s=412`). 새로고침, 화면 회전, 창 크기 변경, 글꼴 로딩 뒤에도 같은 문장이 보인다
- 첫 진입 위치: URL → `last_position` → 1장 첫 쪽
- 화면에 보이는 문장 범위(`chapter_no`, `first_sentence`, `last_sentence`) 계산. 두 쪽이면 왼쪽 쪽의 첫 문장부터 오른쪽 쪽의 마지막 문장까지
- 리더 상단 막대: 책 목록으로 돌아가기, 책 제목·챕터 제목, 목차 열기, 테마 버튼
- 리더 하단 막대: 이전/다음 버튼, 쪽수(한 쪽 `3 / 12`, 두 쪽 `3–4 / 12`)
- 목차 서랍: 챕터 목록, 현재 챕터 표시, 눌러서 이동
- 리더 전용 레이아웃 (일반 헤더와 `main` 여백 없이 화면 전체 사용)

### 하지 않는 것

- 위치 알림 API 호출, 음악 재생·멈춤 버튼, 반응 기록 → 다음 phase (음악)
- 마지막 읽은 위치를 서버에 저장 (위치 알림이 저장을 겸하므로 음악 phase에서 함께)
- 글자 크기·줄 간격·서체 설정, 한 쪽/두 쪽을 사용자가 직접 고르는 설정, 책갈피, 형광펜, 검색
- 종이가 말려 넘어가는 3D 효과 (디자인 시스템 5장: 튀는 효과·큰 회전을 쓰지 않음. 평면 슬라이드만)
- 테스트 프레임워크 추가 (아래 열린 질문)

### 화면 구성

```
┌───────────────────────────────────────────────┐
│ ← 책 목록   봄·봄 · 2장            목차  테마  │  상단 막대 (h-14)
├───────────────────────────────────────────────┤
│                                               │
│   ┌──────────────┐     ┌──────────────┐       │
│   │ 왼쪽 쪽      │     │ 오른쪽 쪽    │       │  본문 영역
│   │              │     │              │       │  (100dvh − 막대 두 개)
│   └──────────────┘     └──────────────┘       │
│                                               │
├───────────────────────────────────────────────┤
│      ‹            3–4 / 12             ›      │  하단 막대 (h-14)
└───────────────────────────────────────────────┘
```

- 두 쪽 모드: `(min-width: 1024px) and (orientation: landscape)`. 데스크톱 창, 태블릿 가로가 해당한다. 그 밖(휴대폰, 태블릿 세로, 좁은 창)은 한 쪽 모드.
- 한 쪽의 글줄 너비는 최대 660px(`max-w-165`, 디자인 시스템 2.2). 두 쪽이면 펼침 전체 너비가 `2 × 660px + 가운데 여백`을 넘지 않게 하고 화면 가운데에 둔다.
- 가운데 여백(제본선 자리)은 데스크톱 80px(`20`), 쪽 바깥 여백은 모바일 16px / 데스크톱 40px. 두 쪽 사이에는 장식선이나 그림자를 넣지 않는다 (디자인 시스템 2.3: 면과 여백으로 구분).
- 본문 서체와 크기: `body-lg`(Pretendard 16px)에 줄 간격 1.8. Phase 06 화면과 같다.

### 페이지 나누기 방식

CSS 다단(multi-column)을 쓴다. epub 리더들이 쓰는 방식이다.

1. 본문 영역의 높이를 고정하고(`100dvh` − 상단 막대 − 하단 막대 − 위아래 여백), 단 너비를 **쪽 하나의 너비**로 둔다. 한 쪽 모드는 영역 너비, 두 쪽 모드는 `(영역 너비 − 가운데 여백) / 2`. `column-gap`은 두 쪽 모드의 가운데 여백과 같게 둔다. 브라우저가 글을 세로로 채우다 넘치면 오른쪽 단으로 넘긴다. 단 하나가 쪽 하나다. 줄 단위로 단이 나뉘므로 글줄이 중간에 잘리지 않는다.
2. 바깥 영역은 `overflow: hidden`이고, 안쪽 띠를 `translateX`로 옮겨 한 번에 한 쪽(한 쪽 모드) 또는 두 쪽(두 쪽 모드)만 보이게 한다. 한 번 넘길 때 움직이는 거리 = 보이는 영역 너비 + 단 간격.
3. 쪽 수 = `scrollWidth / (단 너비 + 단 간격)` (올림). 펼침 수 = `ceil(쪽 수 / 2)`. 두 쪽 모드에서 챕터의 쪽 수가 홀수면 마지막 오른쪽 쪽은 빈 쪽이다.
4. 문장마다 `<span data-sentence-idx>`가 있다 (Phase 06). 각 문장의 `getClientRects()` 위치로 어느 쪽(들)에 걸치는지 구해 `문장 → 쪽` 표를 만든다. 보이는 범위는 지금 보이는 쪽(들)에 조금이라도 걸친 첫 문장과 마지막 문장이다.
5. 이 표는 영역 크기, 한 쪽/두 쪽 모드, 글꼴 로딩, 챕터 본문이 바뀔 때만 다시 만든다. 다시 만든 뒤에는 URL의 문장 번호 `s`가 들어 있는 쪽(두 쪽 모드면 그 쪽이 든 펼침)으로 이동한다. 그래서 화면을 돌려도 읽던 문장이 사라지지 않는다.

### 슬라이드와 드래그

- 넘길 때는 띠의 `translateX`를 바꾸고, `motion-safe:transition-transform duration-300 ease-in-out`으로 미끄러지게 한다. 드래그 중에는 전환을 끄고 손가락 위치를 그대로 따른다.
- 드래그는 본문 영역의 Pointer 이벤트(`pointerdown`·`pointermove`·`pointerup`·`pointercancel`, `setPointerCapture`)로 처리한다. 터치와 마우스가 같은 코드로 동작한다.
  - 가로로 10px 넘게, 그리고 세로보다 많이 움직여야 드래그로 본다. 그보다 적게 움직이고 놓으면 탭으로 보고 좌우 1/3 영역 규칙을 따른다.
  - 놓을 때 이동 거리가 보이는 영역 너비의 20%를 넘거나, 속도가 0.5px/ms를 넘으면(이벤트 `timeStamp`로 계산) 그 방향으로 넘긴다. 아니면 제자리로 미끄러져 돌아간다.
  - 책의 처음·끝에서 더 끌면 저항을 줘서(이동 거리의 1/3만 따라옴) 더 없다는 것을 보여 준다.
  - 본문 영역에 `touch-action: pan-y pinch-zoom`을 줘서 가로 끌기는 리더가 받고, 확대는 브라우저에 남긴다. 드래그 중에는 글자 선택을 막는다(`select-none`).
- 챕터 경계: 마지막 쪽에서 넘기면 띠가 한 화면 밀려 나가고(`transitionend`), 다음 챕터로 바꾼 뒤 그 첫 쪽이 반대편에서 들어온다. 다음 챕터 본문은 미리 받아 두므로(아래 "화면과 상태") 기다림 없이 이어진다. 끄는 도중에 챕터 경계를 넘을 때는 빈 쪽 면이 따라오고, 놓으면 같은 순서로 넘어간다.

### 위치 상태

- URL이 기준이다: `/books/:bookId?chapter=N&s=M`. `s`는 지금 보이는 첫 쪽(두 쪽 모드면 왼쪽 쪽)의 첫 문장 번호.
- 페이지를 넘길 때 `setSearchParams(..., { replace: true })`로 바꾼다. 페이지마다 방문 기록이 쌓이지 않게 한다. 챕터를 바꿀 때만 기록을 남긴다(뒤로 가기로 이전 챕터).
- 잘못된 값: `chapter`가 범위 밖이면 1장, `s`가 그 챕터 범위 밖이면 챕터 첫 쪽.

### 조작과 접근성

| 동작        | 입력                                                                       |
| ----------- | -------------------------------------------------------------------------- |
| 다음 페이지 | 다음 버튼, `→`, `PageDown`, `Space`, 화면 오른쪽 1/3 탭, 왼쪽으로 끌기     |
| 이전 페이지 | 이전 버튼, `←`, `PageUp`, `Shift+Space`, 화면 왼쪽 1/3 탭, 오른쪽으로 끌기 |
| 목차        | 상단 막대 버튼 → 서랍(포커스 가둠, `Esc`로 닫기)                           |

- 두 쪽 모드에서는 한 번에 한 펼침(두 쪽)씩 넘어간다.
- 버튼은 아이콘만 있으므로 `aria-label`("이전 페이지", "다음 페이지")을 단다. 책의 처음·끝에서는 비활성.
- 쪽수 표시는 `aria-live="polite"`로 바뀔 때 읽어 준다 ("12쪽 중 3쪽", 두 쪽이면 "12쪽 중 3–4쪽").
- 키보드 단축키는 목차 서랍이 열려 있거나 입력창에 포커스가 있으면 무시한다.
- 화면 탭 영역과 드래그는 버튼과 별개인 보조 수단이다. 보이는 영역은 `overflow: clip`이라 포커스나 찾기(Ctrl+F)가 띠를 몰래 스크롤하지 못한다. 본문에는 링크·버튼이 없어 Tab이 화면 밖 쪽으로 가지 않는다. 스크린 리더는 챕터 글을 처음부터 이어 읽는다 (책을 읽어 주는 동작으로 자연스럽다).
- 키보드: 입력창에 포커스가 있으면 모든 키를, 버튼·링크에 포커스가 있으면 Space만 양보한다 (화살표는 버튼을 누른 뒤에도 계속 넘김).

### 화면과 상태

- 로딩: 책 정보 로딩 중에는 상단 막대 자리 스켈레톤, 본문 로딩 중에는 본문 자리 스켈레톤 줄. 페이지 계산 전에는 본문을 숨겨 깜빡임을 막는다.
- 에러: Phase 06 규칙(401, 404, 그 밖 + 다시 시도)을 리더 레이아웃 안에서 보여 준다. 본문만 실패하면 상단 막대와 목차는 그대로 쓸 수 있다.

## 위험과 열린 질문

- **CSS 다단 계산의 브라우저 차이**: Safari는 다단에서 `getClientRects()`와 `scrollWidth`가 다르게 나오는 경우가 있다. Chrome·Safari·Firefox에서 확인하고, 문제가 크면 문장 단위로 직접 높이를 재서 나누는 방식으로 바꾼다 (계획 변경으로 기록).
- **모바일 브라우저 주소창**: 주소창이 나타나고 사라지면 `100dvh`가 바뀌어 페이지가 다시 나뉜다. 읽던 문장으로 돌아오긴 하지만 스크롤 중 깜빡일 수 있다. 문제가 되면 `100svh`(가장 작은 높이)로 고정하는 쪽을 검토한다.
- **가장자리 제스처 충돌**: iOS Safari는 화면 왼쪽 끝에서 오른쪽으로 끌면 "뒤로 가기"를 한다. 리더의 "이전 페이지" 끌기와 겹칠 수 있다. 실제 기기에서 확인하고, 필요하면 가장자리 몇 픽셀은 드래그 시작에서 뺀다.
- **문장이 쪽을 넘어갈 때**: 한 문장이 두 쪽에 걸치면 두 쪽 범위에 모두 들어간다. BE가 이 겹침을 괜찮게 보는지 음악 phase 전에 BE와 확인한다.
- **두 쪽 모드의 기준(가로 1024px)**: 큰 휴대폰 가로(약 900px)는 한 쪽으로 남는다. 실제로 써 보고 기준을 조정할 수 있다. 사용자가 직접 고르는 설정은 이번 범위 밖이다.
- **본문 서체**: 소설 본문은 바탕체(`font-display`, Gowun Batang)가 더 어울릴 수 있다. 디자인 시스템은 본문을 Sans로 정했으므로 이 phase는 Sans로 하고, #3 와이어프레임에서 정해지면 바꾼다.
- **테스트**: `paginate`·`spreadOf`·`decideSwipe`는 순수 함수라 단위 테스트를 붙이기 좋다. 다만 테스트 프레임워크(Vitest)는 새 의존성이라 따로 phase를 열지 정한다. 이 phase는 브라우저 확인으로 검증한다.
- **페이지 넘김 연타**: 위치 알림을 얼마나 묶어 보낼지는 BE가 FE와 합의할 항목으로 남겨 두었다 (API.md 5절). 이 phase는 범위 계산까지만 하고, 묶는 규칙은 음악 phase에서 정한다.
